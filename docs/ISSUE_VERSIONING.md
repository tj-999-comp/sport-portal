# Issueのバージョン運用

## タイトル形式

すべての新規GitHub Issueのタイトルは、次の形式にする。

```text
[vMAJOR.MINOR.PATCH] Issueの概要
```

例: `[v2.0.1] NPB本番更新の認証エラーを修正する`

バージョンはIssueごとの通し番号ではなく、そのIssueの変更を取り込む予定のリリースを表す。同じリリースに属する複数のIssueは同じバージョンを使う。親Issueと子Issueも、同じリリースを対象とするなら同じバージョンにする。

## バージョンの決め方

Semantic Versioningに沿って、現在のリリース基準から次の対象バージョンを決める。

- **MAJOR**: 互換性を壊す変更、大きな製品構成の変更、または既存の使い方を移行させる変更。
- **MINOR**: 既存機能との互換性を保った機能追加、新しいリーグや大きな機能領域の追加。
- **PATCH**: 不具合修正、小規模な改善、運用・ドキュメント修正。

複数Issueをひとつのリリースにまとめる場合は、そのリリースに含まれる変更のうち最も大きい区分に合わせる。バージョンはIssueを作るたびに上げず、リリース単位で共有する。

## このリポジトリの基準

- 現在の基準リリースは **v2.0.0**。4リーグ構成とNBA Production更新WorkflowをMainへ統合した版として扱う。
- 互換性を保つ次の機能追加は **v2.1.0**、v2.0.0系列への修正は **v2.0.1** を初期候補とする。
- 互換性を壊す次の大きな変更は **v3.0.0** を初期候補とする。
- 新しいIssueでは、現在のリリース基準と対象変更を確認してからバージョンを決める。上記の候補は目安であり、すでに別リリースが始まっている場合は最新の基準を優先する。

## Issue作成・変更時

1. Issueの受入範囲と対象リリースを決める。
2. 上記のルールでバージョンを選び、タイトルの先頭に付けてIssueを作成する。
3. 既存Issueの範囲が別リリースへ移った場合は、タイトルのバージョンも更新する。
4. Issueをクローズしても、当時のタイトルとバージョンは履歴として保つ。

バージョンはIssueの計画ラベルであり、リリース完了や本番反映を意味しない。リリースおよび環境反映の承認・確認は別途記録する。
